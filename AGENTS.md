# PipeFlow CRM — regras do projeto

## Estrutura
- DeskData uses one shared read-only financial projection and documented basic fields; unknown turnover stays absent, keeping capital separate from revenue.
- B2B subroutes render inside one persistent B2bWorkspace using AreaLayout; Receita selections carry CNPJ-keyed unreviewed CompanyData without Maps IDs into the existing confirmed import. Receita reads reuse the saved custom integration "Receita Federal - CNPJ" (Basic Auth decrypted server-side) against its PostgREST GET endpoint, require a filter and page 50 rows server-side; no direct PostgreSQL connection or VPS/index changes.
- Receipt Control reuses canonical charges/payments/reconciliation; monthly columns rank actual client due dates before filters, never synthesize charges. Explicit bounded schedules alone create missing occurrences; corrections preserve bank/payment IDs and audit. Financeiro renders only Outlet on this child to avoid duplicate screens.
- WhatsApp group selection reads service-only snapshots keyed by verified company, instance and canonical binding phone; leased synchronization stores essential metadata only, while selected-group live permission checks gate queueing and each group send, so cached data never authorizes delivery.
- Pipeline bulk deletion reuses deleteCrmLeads and snapshots selected ids from the open funnel in a confirmation dialog; failed writes retain selection, preventing false success or deletion of unselected cards.
- Customer Success reuses Clients and private conversation ownership checks; structured management/criteria/contracts share the revision-bound CS audit, and recovery uses existing client tasks. This keeps reviews independent of WhatsApp and financial writes; see src/lib/AGENTS.md.
- Read src/lib/AGENTS.md: B2B private imports/AI drafts (30, leased, review-only); Projects/Universe admin service-only. /gravon-universe is the lab Universe ported unchanged from gravoncompany/lead-flow-sandbox@develop f04fad5 (WebGL planets, journeys, celebration; journey module renamed gravon-universe-journey), fed by the verified Sheets reader ('2026' E1:P1, E51:P52 'Valor Total', E54:P55 'Tráfego'); lab simulation stays disabled. Access is via the header profile pop-up (crm_profile, 0082); the bell sits beside 'Atualizar pipeline' on the Pipeline page.
- Reference messages (0083) map campaign texts (exact/contains, Google/Meta) to any funnel/stage; capture is service-only, idempotent per message, never duplicates a contact's card in the same funnel and only fills empty origin/UTM. The per-funnel Commercial Agent (0084) is default-off with test-number audience, revision-bound settings, DB claims/leases, grounded replies (cited knowledge, numbers from knowledge), human handoff/holds, no resend on unknown outcomes and evidenced forward-only moves; webhook hooks run after persistence and never change its response. See docs/commercial-agent-crm-readiness.md.
- Vite: 8 GiB; validate HTTPS/public bindings, preserve VITE/generated clients. Public fallback only if env absent.
- Portal subject: crm:evolution:v1: + SHA-256(JSON [origin, instance, canonical sender]); remove only Brazil's optional ninth digit. Require private claim, live self instance, exact key.id/fromMe; LID needs addressingMode=lid + exact remoteJidAlt. Query key.id only. Recheck bearer admin/channel for disclosure; no raw data/secrets. Manual fetch rejects redirects; 10s timeout requires aborted signal/TimeoutError. Strict tool args rechecked; validate list options/pagination; oversized replies fail closed; distinguish credential configuration failures.
- Lead notifications derive from persisted history; the CRM sidebar mounts the bell/pop-up only behind the CRM gate; the latest-update callout lives in the lead sheet. A BEFORE UPDATE trigger preserves audited history; browser-local read markers never authorize.
- Additional sales pipelines are private service-only records managed through full signed CRM-session server functions; nullable lead pipeline_id preserves the original pipeline and legacy integration inserts. Scope Pipeline cards, totals, list selection and new-lead stages to the selected funnel; keep original browser-stored stages and other integrations compatible.
- Personal WhatsApp stage writes use a separate default-off grant plus service-only proposal/resolve RPCs with settings/action/lead locks; the model can only propose. Exact later Confirmar/Cancelar commands resolve a single unexpired proposal predating the inbound claim, with durable resolution replay, version checks and audit. Keep coded legacy commands compatible, effects independent of WhatsApp delivery and internal chat tool-free.
- Leads carry a database-incremented revision for WhatsApp proposal concurrency; a trigger rejects stale history replacement that would erase a confirmed action so legacy full-row editors cannot silently undo audited moves.
- WhatsApp: private settings, atomic dedup, own-number/AI-loop guards; no cap. Campaign channels require verified admin and exclusive tenant/number bindings, never connection-as-permission. Read src/lib/AGENTS.md.
- CRM reads from personal WhatsApp require a separate default-off phone/instance/revision grant, rechecked per bounded read RPC and before sending; expose only bounded counts, exact lookup and shared entry-cohort funnel metrics. Financial and closed-potential values require an independent default-off grant bound to the read revision and authorized number; validate it before cache/connector/RPC access and sending. Never expose generic queries or internal-chat tools.
- Gravon WhatsApp authorization compares complete normalized numbers with only Brazil's optional leading mobile ninth digit allowed; reuse sameWhatsAppNumber for diagnostics, inbound checks, revalidation and provider receipts, never phoneKey for send authorization.
- Gravon WhatsApp test processing uses an atomic structured inbound claim and a service-role-only accepted-message persistence RPC; provider acceptance is not delivery, recovery retries only persistence, and legacy logs are never reconstructed from current instance settings.
- Internal chat: full cookies/history; knowledge requires bearer admin/company. Write confirmations use DB tool results only; event/tool logs omit content. Floating chat suspends inline writers.
- Individual email accounts are additive for Portal, no profiles/auto-admin. Service-only role/channel grants require verified email; bearer getUser + own RLS rows authorize exact channel disclosure. Root sign-out clears private state; keep legacy CRM gate until isolated cutover.
- Lead UTMs: shared lead-attribution module, persisted apart from editable data. Zapier needs secret token or full CRM session; optional pipeline_id (first stage) and event_id (claim table) dedupe; payloads without them keep legacy inserts.
- WhatsApp analysis itself never modifies leads and validates literal inbound qualification evidence. Separate full-cookie-only qualification proposals bind saved analysis, unique matched lead/revision and its own pipeline; Confirmar atomically adds the existing tag, moves the card and appends reviewed internal notes without replacing prior notes via service-only locked RPC with durable replay and protected audit. Cancelar changes no lead. Period runs stay sequential with terminal AI blocks persisted.
- The Financeiro page and authorized personal WhatsApp reuse a fixed-range server-only Sheets reader with a short cache and explicit missing/error states; page session and channel grants are checked separately before cache access. Shared funnel metrics use entry-date cohorts and current built-in stages; closed potential is not received revenue or the lead company's reported revenue.
- CRM password entry is verified server-side and issues an expiring signed HttpOnly cookie (preview/dev only: same token via x-pipeflow-preview-session header, since the iframe drops cookies; ignored when published); financial reads require full access before cache or connector use, so browser storage cannot authorize private financial data.
- Evolution token-checked webhooks store private messages, read through full-cookie functions; never create leads. Conversations match phoneKey; calls require exact normalized contact and registered tenant/instance, reject ambiguity/LID, and never infer outcomes. Locked service-only RPC writes calls/manual interactions into leads.history; private receipts only deduplicate/diagnose. Manual full-cookie writes stay in legacy crm:1. CALL setup preserves webhook settings.
- Knowledge tab reuses ai_knowledge: generated insights remain append-only, manual records persist independently of generations. Company/author come from verified admin channels, never model inputs; private service-only writes recheck admin/company, deduplicate event keys and enforce revisions. WhatsApp also requires existing knowledge grant plus live Evolution event/identity. AI updates append; menu replacement is explicit. Learning: manual, leased, no self-chat, completed runs only; no lead changes/sends/training.
- Finance/Polp: private ledger, admin-owned personal scopes, Clients references, separate Sheets/Portal, read-only AI. Polp catalog only, no auth proof. See src/lib/AGENTS.md.
- Portal art WhatsApp notifications use an independent bearer + raw-body HMAC route, default-off env gate, explicit consent and service-only notification reservations; never log approval URLs/bodies and never retry sending/unknown outcomes.
- Instagram OAuth/webhook rules live in src/routes/api/public/instagram/AGENTS.md; read it before changing src/lib/instagram* or those routes.
- B2B Instagram prospecting (b2b-instagram*) calls the Apify Instagram Scraper server-side only, with the Bearer token decrypted from the custom integration row; paid hashtag runs need explicit confirmation, 24 h reuse, daily metering and cancellation, and profiles enter the CRM only through the existing reviewed import with origin "Instagram - Apify", deduped by profile URL. AI analysis is grounded, batched and optional; no messages are ever sent from this module.
- Main-funnel auto-qualification + prepared Meta lead events: see src/lib/AGENTS.md.
