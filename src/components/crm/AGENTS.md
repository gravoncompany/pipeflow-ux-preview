# CRM component rules
- Main navigation uses exactly the nine MAIN_NAV_ITEMS (including Marketing) with no category headings or child shortcuts; area matching covers existing child paths. The Marketing area (/marketing/*) renders inside MarketingLayout with its six submenus (Visão Geral, Campanhas, Fontes de Aquisição, Funil de Conversão, Eventos e Conversões, Análises IA); ad accounts feeding it live in marketing_integrations per company, enabled explicitly by the user, never auto-discovered into dashboards. AreaLayout adds shared management links on existing Metas/Financeiro/Projetos screens while preserving their section menus and Projects permission gate; no management route or second sidebar.
- Conversations uses isolated channel branches; Instagram reuses its admin/company server reads and contact IDs, never the WhatsApp phone, sending or analysis components, so switching tabs cannot mix identities.
- Analysis next-message UI keeps edits on failure, confirms replacement only, and authorizes exactly one displayed draft/text with one send click. Contact/scope keys isolate local state; uncertain sends require status checks, never automatic retry. Current period analysis/qualification remains separate from the fresh draft justification.
- Commercial goals: service-only rows per month+pipeline ("main" = null) via full-session functions; null = not informed; duplicates never overwrite. Traffic investment: service-only per pipeline+period; full months reuse the goal adSpend.
- Commercial goals dashboard is read-only presentation using existing calculation helpers; its configuration dialog retains the original editor and save actions so presentation changes do not alter persisted data or financial rules.
- Funnel acquisition (Funil page) reads Gravon-owned Meta API spend (meta-funnel-ads*, imported meta_ads_spend_daily) with exact campaign links in portal_ads_campaign_links, never Portal snapshots through a browser-safe helper. The spend component surrounds the chart to share one query with collapsed source details; CAC de mídia divides linked-campaign spend by unique new customers from confirmed sale classifications, never by raw closed opportunities.- Commercial Agent panel lists every active funnel with its own state and switches settings per funnel inside the sheet, grouped as Atendimento / Instruções e qualificação / Regras do Pipeline / Atendimento humano e limites; reply stages (allowed_stages) and move stages (move_stages, 0103: NULL = legacy stage mapping, [] = never move) are independent permissions enforced in decideAgentMove and apply_crm_agent_decision. Templates (Pipeflow CRM) only prefill the form, never save, enable or carry prices—commercial conditions stay in Commercial Knowledge.
- LeadDetailSheet is the single lead card (Pipeline full-height right-side panel on ≥1024px rendered as a sibling of the page column so it spans top to bottom and scrolls inside, full-screen sheet with "Voltar ao quadro" on smaller screens, inline in Conversas): Resumo (filled main fields name/company/WhatsApp/e-mail/Instagram/origin/stage/service, next step saved alone on the stored card, latest update), Atividade (read-only merged timeline via lead-timeline plus the existing notes/WhatsApp/e-mail views) and Dados do lead (read-only until Editar). Pipeline pending shortcuts reuse getDashboardToday lists filtered to the open funnel (pipeline-pending), never a second rule set.
- Per-lead Gravon IA control is keyed by the contact's crm_phone_key (0088, service-only, revision-bound) and shared by the card and Conversas through one query key; it can only restrict the funnel agent (claim and pre-send both recheck it), never widen audience, stages or hours. Conversas unread badges use browser-local read markers only; the full card opens inline only on explicit click.
- Multi-screen areas render inside AreaLayout (white grouped secondary menu modeled on the Gravon IA internal menu, Sheet + ☰ bar on mobile): SettingsLayout/SETTINGS_GROUPS for /configuracoes/*, AtendimentoLayout/ATENDIMENTO_GROUPS for /whatsapp, /clientes(/*), /contatos and /agenda(/*) (one AgendaWorkspace with the existing calendar functions), and DashboardLayout (/dashboard, /dashboard/insights; period lives in search params so both share it). CampaignsLayout groups /campanhas (e-mail), /campanhas/whatsapp (file campanhas_.whatsapp.tsx, same CampaignPage locked to its channel), /fluxos-email and /automacoes(/*). Shortcuts open cards via /?lead=<id> (CrmBoard selects the lead's funnel) and meetings via /agenda?reuniao=<id>. Add new screens to those groups instead of per-page links; single-screen areas keep CrmSidebar directly. Main menu order/area matching lives in CrmSidebar GROUPS + crm-nav.mainAreaActive.
- The CRM home (/) is titled "CRM" with Kanban (default) and Análise de Funis tabs in ?aba=funil; both share the funnel selected in usePipelines (FunnelAnalysis is controlled by CrmBoard there). The /funil route is preserved and renders the same FunnelAnalysis component standalone (uncontrolled); its metrics, period presets and spend panel are unchanged.
- Client page (/clientes/$id, file clientes_.$id.tsx so it is not nested in the list) opens on Visão geral with tabs in ?aba=; Cadastro reuses ClientForm/saveClient, Histórico is the read-only merge in client-history.ts. Phase 1 (0107, crm-client-phase1.functions + ClientPhase1.tsx): crm_client_projects (many per client, optional crm_projects link, documents via crm_client_documents.project_id); campaign indicators come only from ad accounts bound to that client (crm_client_ad_accounts, unique per platform account) read from the existing Portal agency snapshot plus client-bound Meta API spend, never summing both sources for Meta; leads/CPL stay "Sem dado" until the Portal sends per-company leads; the Gravon IA report is stored as crm_client_knowledge kind relatorio_ia. Lead→client conversion/review prefill uses the B2B profile without overwriting card data and reuses the client of an identical CNPJ. The Clientes list keeps search/situação in URL params and saves them plus scroll in sessionStorage (client-list-state) for "Voltar para clientes".
- Fechado (0104): leads.closed_value/closed_value_confirmed_at are written only by the service-only confirm_lead_closed_value RPC (full session, stage must be 'fechado', appends history); the card save never writes them. Pipeline header totals (pipeline-totals) run over the filtered cards: Potencial = open stages (not fechado/perda), Valor fechado = confirmed values. Moving to Fechado opens ClosedValueDialog then SaleCloseDialog. "Adicionar como cliente" (card + bulk, AddClientsDialog) reviews a lead-to-client draft and saves via addLeadAsClient (save_crm_client with lead link; existing link returns the existing ficha). /whatsapp?contato=<phone_key> opens that conversation.
- Prospecção B2B is one route with steps in ?etapa= (buscar default, revisar, contato) under a sticky top submenu; search results, selection, prepared/enriched data and session-created lead ids persist in sessionStorage (b2b-flow) so step, Cards/List and page changes never drop selections, and a new search keeps previously selected places. "Registrar abordagem" writes a manual lead interaction whose text starts with FIRST_CONTACT_PREFIX; getB2bOverview derives approaches from lead history, so status needs no extra table.
- Financeiro is one layout route (/financeiro renders FinanceManagement inside AreaLayout with an Outlet); child routes /financeiro/{movimentacoes,custos,planejamento,analise,pessoal} render null and finance-nav maps the path to a section grouping the existing tabs, so switching screens keeps state. The pessoal section is the only personal-scope view (no in-page scope selector); the business view never shows personal expenses. The Faturamento Confirmado section uses one full-width "Evolução do Faturamento" chart plus year-scoped indicators (accumulated, best month, average over elapsed months) from getFaturamentoAnual, which applies the unified confirmed-revenue rule (Financeiro receipts + bank-confirmed client revenue, counted once; RDB/own-transfers/personal excluded) via yearEvolution + yearlyRevenueStats. PolpConnection stays mounted (hidden outside Movimentações › Extrato bancário) to keep its auto-sync. Melhorias do Pipeflow (/projetos, /projetos_/em-andamento, /projetos_/concluidas) group existing project statuses via pipeflow-improvements; no new statuses.
- Campaign recipients are lead ids plus, for WhatsApp only, direct crm_clients ids (crm_campaigns.client_ids, 0125): a client with a card goes through its card (linked lead, else the single same-WhatsApp card); a client without one is reviewed by itself under the same consent/suppression rules and no card is ever created. Conversas selections still hand lead ids via sessionStorage CAMPAIGN_SELECTION_KEY; Conversas Cards/Lista share page-level search/filters/selection.
- Clientes list card actions (client-card-links, 0125): only crm_clients.lead_id counts as linked ("Abrir card" → /?lead=); WhatsApp/e-mail/company matches are suggestions for manual linking only. "Criar card no CRM" creates one main-funnel Fechado lead per client via locked service-only RPC; never in bulk.
- Insights › Prospecção Outbound keeps the general KPIs; E-mail/WhatsApp tabs and the consolidated funnel come from outbound-channels (pure) + .server (Brevo events read by messageId, Evolution messages by unique phoneKey). Each Outbound lead has one origin channel = its first recorded contact, so the funnel never double counts. Outbound automatic tags (outbound-auto-tags) are derived on read from automation runs, Brevo-accepted sends and diagnosis forms, shown as outline chips and "· automática" filter options only on the Outbound funnel; they are never written to leads.tags.
- O assistente de IA do CRM é apresentado como "Pipeflow IA" (antes Gravon IA) em toda a interface; arquivos, funções, tabelas e as páginas legais/de acesso individual do Portal mantêm os nomes antigos. O botão flutuante e o avatar do chat usam o logotipo oficial do Pipeflow (PipeflowSymbol), não mais o robô.
- WhatsApp campaigns (/campanhas/whatsapp) use whatsapp-campaign/WhatsAppCampaignStudio: 4-step wizard; audience is either groups (sent to the @g.us JID, re-verified via Evolution fetchAllGroups for membership/announce-admin) or individuals (leads/clients/manual/CSV) never mixed (0135 enforces); whatsAppTargets is the single recipient resolver and normalizeWhatsAppTarget the only phone normalizer (55 added, @lid/@g.us untouched).
